# Feature Specification: Platform foundation

**Feature Branch**: `001-platform-foundation`

**Created**: 2026-09-30

**Status**: Draft

**Input**: Parent roadmap: `specs/tenancy-hub-platform/roadmap.md` → entry **R1**. Multi-tenant SaaS shell with per-agency isolation, organizational sign-in, roles, audit, and notifications; shared application chrome so future domain modules plug in behind stable tenancy boundaries.

## Clarifications

### Session 2026-09-30

- Q: When a user's work account is disabled in their organization's directory but they still have an active Tenancy Hub agency membership, should Tenancy Hub block their access on the next authentication check (not only at the next interactive sign-in)? → A: Block on next sign-in or token/session validation; no operational work until the directory account is restored or membership is removed.
- Q: When an agency is deleted or archived, should platform operators retain read-only access to that agency’s historical audit records while members can no longer sign in or operate in that agency? → A: Support archived state—members cannot operate; audit remains readable by platform operators per policy; physical delete of audit data is out of scope for R1.
- Q: When a user who belongs to multiple agencies switches their active agency in the shell, should in-progress work tied to the previous agency be discarded and all subsequent requests scoped only to the newly selected agency? → A: Agency switch immediately changes active context; discard unsaved/in-flight UI work for the prior agency; block or fail operations still tied to the old agency.
- Q: When two administrators update the same member’s roles in one agency at nearly the same time, should the last successful update determine the member’s effective roles while each attempt is recorded in audit? → A: Last successful role update wins; every attempt is auditable; duplicate pending invites for the same identity in the same agency collapse to a single pending membership.
- Q: In R1, should platform operators help agencies using read-only cross-agency access (provisioning, audit, support diagnostics) without impersonating a member’s signed-in session? → A: Cross-agency provisioning and read-only support views (audit, diagnostics); no member impersonation in R1; every cross-agency access is auditable.
- Q: When a user's session expires or authentication fails during validation while they have unsaved or in-flight work, what should the product require before they can continue? → A: Extend session on user activity up to a maximum working-day cap; when the cap is hit or validation fails, require sign-in again, discard unsaved client state, and fail safely any in-flight operations.
- Q: While an agency is suspended (not archived), should agency members be allowed to sign in at all? → A: Members cannot sign in while suspended; clear suspension message; platform operators can still manage the agency.
- Q: For R1, should user notifications be delivered only inside the signed-in application shell? → A: In-app shell notifications only in R1 (no email or push).
- Q: For shell navigation entries the signed-in user is not allowed to use in R1, should those entries be hidden entirely or shown in a disabled state? → A: Hide navigation entries the user cannot access (default R1 policy).
- Q: In R1, which roles may invite or provision new members into an agency? → A: Agency administrators and platform operators.
- Q: For R1, should the product ship a distinct read-only agency member role, or should read-only behavior come only from permissions on the standard member role? → A: Include a distinct read-only member role in the minimum R1 role set (alongside administrator, standard member, platform operator).
- Q: When a platform operator signs in, how should they choose which agency context to work in for day-to-day shell use? → A: Select an active agency at sign-in or via switch (same single active context as multi-agency members), with additional operator-only cross-agency read-only and provisioning actions; each cross-agency access is scoped to the target agency and auditable.
- Q: For R1, how should the shell surface upcoming roadmap modules (for example CRM and properties) before those features ship? → A: No future-module navigation entries; a single home/dashboard placeholder summary for permitted roles only (coming-soon roadmap areas, not disabled nav tease).
- Q: In R1, which agencies may a platform operator select as their active agency or target in cross-agency operator flows? → A: Only agencies explicitly assigned to that platform operator.
- Q: What maximum duration should cap an activity-extended signed-in session before the user must sign in again? → A: 12 hours absolute maximum from initial sign-in (user activity may extend idle timeout but not beyond this cap).
- Q: After how many minutes of user inactivity should an idle signed-in session end and require sign-in again, still subject to the 12-hour absolute cap from initial sign-in? → A: 30 minutes idle (user activity resets the idle timer; absolute 12-hour cap still applies).
- Q: When a user who belongs to more than one agency signs in, should Tenancy Hub open their last-used agency automatically or always require an explicit agency choice before entering the shell? → A: Default to last-used agency if still valid; user can switch in shell.
- Q: In R1, who may create or change which agencies a platform operator is assigned to? → A: Platform operators only, via auditable operator-only assignment management.
- Q: In R1, which agency-level settings should agency administrators be allowed to change in the product? → A: Display name plus primary contact email and phone (operators may set at provision; admins may update for active agencies).
- Q: After how long should a pending agency invitation expire if the invitee never accepts it? → A: 30 days (then invite is no longer valid until re-invited; auditable).
- Q: For R1, must platform operators be able to create new agencies inside Tenancy Hub (not only invite members into agencies that already exist)? → A: Yes—platform operators create agencies in-product (auditable); no self-service agency signup.
- Q: In R1, which roles may change an agency’s lifecycle state (for example suspend, reactivate, or archive)? → A: Platform operators only; agency administrators cannot change agency lifecycle in R1.
- Q: When someone accepts an agency invitation in R1, must they sign in with the same work-account identity (email) that was invited? → A: Yes—sign-in identity must match the invited email; otherwise access is denied.
- Q: In R1, before domain modules ship, which capabilities should a standard agency member have that a read-only agency member does not? → A: Standard member may mark in-app notifications read; read-only may view notifications but not change read state.
- Q: When a platform operator creates a new agency in R1, should that operator be automatically assigned to that agency so they can manage it immediately? → A: Yes—creator is automatically assigned to the new agency (auditable).
- Q: In R1, besides marking in-app notifications as read, should standard agency members be allowed to dismiss or remove notifications from their list, or should notifications stay visible with read/unread state only? → A: No dismiss/remove in R1—standard members mark read only; items remain in the list (read state changes).
- Q: For R1, should agency-scoped audit history remain queryable for the full life of the agency (including after archive), or should the product enforce a maximum retention window after which older audit events are no longer shown? → A: Retain all audit events for the agency’s lifetime (active, suspended, archived); no purge in R1.
- Q: In R1, when an agency would be left with zero agency administrators (for example the last administrator removes themselves or is demoted), should the product block that change until another administrator is assigned? → A: Block the change; require at least one agency administrator at all times.
- Q: In R1, should the same user be allowed to stay signed in on multiple browsers or devices at the same time, or should a new sign-in invalidate other active sessions for that user? → A: Allow concurrent sessions—each device/browser has its own session subject to idle and 12-hour rules.
- Q: While an agency is suspended (members cannot sign in), should platform operators still be allowed to invite or provision new members and change roles for that agency? → A: Yes—platform operators may invite, provision, and change roles while suspended; members still cannot sign in until the agency is active.
- Q: In R1, may a single active agency membership include more than one of the agency roles (administrator, standard member, read-only member) at the same time, or must each member have exactly one agency role per agency? → A: Exactly one agency role per active membership in R1 (administrator, standard member, or read-only member); platform operator access remains separate via operator assignment, not stacked agency roles.
- Q: In R1, when an agency administrator or platform operator “suspends” a user’s agency membership (as distinct from removing it), should that be a real membership state that blocks sign-in for that agency while keeping the membership record for possible reactivation, or should R1 only support remove (no separate suspended membership)? → A: Distinct **suspended** membership state in R1—blocks agency access with clear message; membership and role retained for reactivation by agency administrators or platform operators (auditable); distinct from **removed** (requires new invitation to return).
- Q: After an agency is created in R1, may platform operators update that agency’s display name and primary contact email or phone (for example while supporting a suspended agency), or may only agency administrators change those fields—and only while the agency is **active**? → A: Platform operators may update R1 agency settings on **assigned** agencies via operator flows (including **suspended**); agency administrators may update them only while the agency is **active**.
- Q: In R1, who should be allowed to open the agency-scoped audit history view for an **active** agency (not cross-agency operator tooling)? → A: Agency administrators only (active agency, active membership); platform operators via assigned operator flows; standard and read-only members denied in R1.
- Q: In R1, which events must create an in-app notification for the affected user (not only an audit entry)? → A: Notify affected user on invitation pending acceptance; membership activated; role changed; membership suspended, reactivated, or removed; agency display-name or contact changes that affect displayed agency context (agency administrators may receive the same category of notice where applicable).
- Q: In R1, may platform operators move an archived agency back to active (or only to suspended), or is archive a one-way terminal state with no return to operational use until a later release? → A: Operators may reactivate archived agencies to **active** (or **suspended** then **active**) in R1; members can work again after the agency is **active** per normal rules; transition is auditable.
- Q: In R1, which signed-in roles may view the agency’s member list (names and roles only—no invite or role changes)? → A: Agency administrators and platform operators manage membership; **standard members** may view the member list read-only; **read-only members** may not view the roster in R1.
- Q: In R1, may agency administrators or platform operators cancel or revoke a pending invitation before it expires or is accepted? → A: **Agency administrators and platform operators** may revoke pending invitations (immediate invalidation; auditable; re-invite required to accept).
- Q: For the R1 home coming-soon summary of unshipped modules (for example CRM and properties), which agency roles should see that summary while signed in to an active agency? → A: **Agency administrators and standard members** only—**read-only members** do not see coming-soon module summaries in R1.
- Q: In R1, may the same work-account identity be both a platform operator and a member of one or more agencies (with operator assignments and agency memberships enforced separately)? → A: **Yes**—one identity may be operator and agency member; operator and membership capabilities are enforced separately (operator flows vs active agency context).
- Q: When a platform operator creates a new agency that has no member memberships yet, should that agency be allowed to stay **active** with zero agency administrators until someone is invited or provisioned as an administrator, or must the product prevent **active** status until at least one **active** agency administrator exists? → A: **Active** agency may have zero members (and zero administrators) until the first administrator is invited or provisioned; the at-least-one-administrator guard applies once agency administrator memberships exist.
- Q: In R1, when an agency administrator or platform operator adds someone using **provision** (not a pending email invitation), should that person’s membership become **active** immediately, or must every new member still go through **invited** status and accept before becoming **active**? → A: **Invite** → **invited** until accept with matching work-account email; **provision** → **active** immediately (auditable; same identity rules).
- Q: When a user is a **platform operator** but has **no agency assignments** (and no agency memberships), what should happen after they complete organizational sign-in in R1? → A: Sign-in allowed; operator-only global flows (create agency, manage operator assignments and **platform operator** status); no active agency shell context until at least one assignment (including auto-assign on agency create).
- Q: In R1, must each agency’s **display name** be unique across the entire Tenancy Hub product, or may multiple agencies share the same display name because tenancy is keyed by an internal agency identity? → A: Duplicate display names allowed; internal agency identity is canonical.
- Q: In R1, when inviting or provisioning by work-account email, may administrators target an email that is not yet a sign-in-capable user in the customer’s directory, with access only once that person can sign in with the matching identity? → A: Invite/provision any valid work-account email; no directory pre-existence check; agency access only when sign-in matches identity (and invite accept rules for **invited**).
- Q: When someone signs in with a work account that matches one or more pending **invited** agency memberships but they have no **active** agency membership yet, what should they see before they can use the normal agency shell? → A: Sign-in succeeds; dedicated in-product invitation-acceptance experience; routine agency shell for an agency only after explicit per-invite accept with matching identity (no auto-activate on sign-in alone).
- Q: When an administrator or platform operator sends an **invite** (not a **provision**), must they choose the invitee’s agency role at invite time, and should that be the role the person gets when they accept? → A: Inviter must select administrator, standard member, or read-only member at invite; on accept, membership becomes **active** with that role (auditable).
- Q: While a person’s agency membership is still **invited** (not yet accepted), may an agency administrator or platform operator change the agency role that will apply when they accept? → A: **Agency administrators** and **platform operators** may change role on **invited** membership until accept, revoke, or expiry (auditable); accept applies the current role at accept time.
- Q: In R1, may one platform operator grant or revoke another person’s **platform operator** status inside the product (separate from per-agency assignments), and who is allowed to do that? → A: **Platform operators** may grant or revoke **platform operator** status on work-account identities in-product (auditable); agency administrators cannot.
- Q: In R1, should the product block revoking **platform operator** status when that change would leave zero platform operators in the system? → A: **Block** revoke or self-revoke that would leave zero **platform operators**; clear message; auditable attempt.
- Q: While an agency is in **archived** status, may platform operators still invite, provision, or change roles for that agency, or must those membership changes wait until the agency is reactivated to **active** or **suspended**? → A: **Archived** blocks invite, provision, and role changes until reactivation to **active** or **suspended**; operators may still view audit and perform lifecycle transitions (including reactivation); members still cannot sign in until the agency is **active**.
- Q: When a platform operator changes an agency’s lifecycle (for example **suspend**, **archive**, or **reactivate** from **archived**), should affected agency members receive in-app shell notifications in R1, or should those events appear only in audit? → A: In-app notifications to users with **active** or **suspended** agency membership (including agency administrators) on agency **suspend**, **archive**, and **reactivate** to **active** or **suspended** (including from **suspended** or **archived**); audit always; **removed** and **invited-only** users are not notified for agency lifecycle.
- Q: For R1 platform-operator “support diagnostics” alongside read-only audit on assigned agencies, what must the product show beyond audit history? → A: Read-only **agency summary** (internal agency identity reference, display name, lifecycle status, primary contact email and phone, membership counts by agency role, timestamp of most recent agency lifecycle change) plus access to full agency-scoped audit; no infrastructure, service health, or distributed tracing telemetry in R1.
- Q: In R1, may an invitee explicitly **decline** a pending agency invitation in the product, or can a pending invite only end through acceptance, operator revoke, or the 30-day expiry? → A: Invitee may **decline** in the invitation-acceptance experience; membership transitions from **invited** to **removed**; accept is blocked until a new invitation; auditable; no separate inviter in-app notification for decline in R1 (audit only).
- Q: For R1, should all signed-in shell and operator-facing user interface copy be **English only**, or must the product support additional languages in this release? → A: **English only** for R1 user-facing copy; no language selector; dates and numbers use UK English conventions; additional languages deferred.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Sign in to the correct agency (Priority: P1)

An agency staff member opens Tenancy Hub, signs in with their work account, and always works inside their letting agency’s workspace. They see only their agency’s name and data context; they never need to pick the wrong organization by mistake.

**Why this priority**: Without trustworthy sign-in and agency context, no other product capability is safe or usable in a multi-tenant SaaS.

**Independent Test**: Can be fully tested by signing in as users from two different agencies and confirming each lands in the correct agency workspace with no cross-visible data.

**Acceptance Scenarios**:

1. **Given** a user who belongs to one agency, **When** they complete sign-in, **Then** they enter the application with that agency clearly indicated and all subsequent actions scoped to that agency.
2. **Given** a user who belongs to more than one agency, **When** they sign in, **Then** they enter the shell with their last-used agency as active context when that agency is still valid for them, **And** they can switch to another agency in the shell at any time; the active choice persists for the session until they switch again.
3. **Given** a multi-agency user with unsaved or in-flight work in Agency A, **When** they switch active agency to Agency B, **Then** the shell re-scopes to Agency B immediately, discards unsaved UI state for Agency A, and does not complete pending operations against Agency A.
4. **Given** a user with no Tenancy Hub agency membership records and who is not a platform operator with permitted global flows, **When** they complete sign-in, **Then** they see a clear message that access is not configured and cannot view agency data.
9. **Given** a user who has one or more **invited** agency memberships but no **active** agency membership (and no other valid path into the shell, such as platform operator assignment), **When** they complete sign-in with a work account matching the invited email(s), **Then** sign-in succeeds, they see a dedicated invitation-acceptance experience (not the routine agency shell), they MUST complete an explicit accept or **decline** action per **invited** membership before that agency becomes shell context, successful accept transitions membership to **active** (auditable; activation notification per FR-010), and **decline** transitions membership to **removed** (auditable; new invitation required to join); **Given** the same user also has at least one **active** membership elsewhere, **When** they sign in, **Then** they MAY enter the shell under last-used valid **active** agency rules while still addressing any remaining **invited** memberships through the acceptance experience without auto-activation on sign-in alone.
5. **Given** a user whose work account is disabled in their organization's directory but still has an active Tenancy Hub membership, **When** they attempt sign-in or any authenticated request is validated, **Then** access is denied with no agency data shown and the attempt is auditable as a failed sign-in or terminated session.
6. **Given** a signed-in user whose session reaches **12 hours** from initial sign-in, **30 minutes** without user activity that resets the idle timer, or fails authentication validation, **When** they attempt further action or have unsaved or in-flight work, **Then** they must sign in again, unsaved client state is discarded, and in-flight operations fail safely without completing under an invalid session.
7. **Given** a platform operator with explicit assignments to one or more agencies, **When** they complete sign-in, **Then** the shell defaults to their last-used assigned agency when still valid (otherwise they choose from their assigned set) and scopes routine work to that agency until they switch; **When** they use operator-only cross-agency read-only or provisioning flows, **Then** the target agency must be one they are assigned to, each action names that agency, does not impersonate a member session, and is auditable; **Given** an agency not assigned to them, **When** they attempt operator or shell access, **Then** access is denied without data leakage.
8. **Given** a platform operator with **no** agency assignments and **no** agency memberships, **When** they complete sign-in, **Then** sign-in succeeds, they see a clear no-agency-assigned context, they have **no** active agency for routine shell work, and they **may** use operator-only global flows in R1 (create agency—with auto-assign on create—manage platform operator agency assignments, and grant or revoke **platform operator** status on identities); **When** they attempt routine agency-scoped shell work or cross-agency operator flows that require a target agency without an assignment, **Then** access is denied or blocked without data leakage until they have at least one assignment.

### User Story 2 - Enforce agency data isolation (Priority: P1)

A user authenticated in Agency A must never read or change records belonging to Agency B, including through direct navigation, shared links, or mistaken identifiers.

**Why this priority**: Tenant isolation is a non-negotiable security property for a commercial multi-tenant product handling letting operations.

**Independent Test**: Can be tested by attempting to access another agency’s resources (by identifier or URL) while signed in as a user of Agency A; every attempt must fail safely without leaking existence or content.

**Acceptance Scenarios**:

1. **Given** a user signed in to Agency A, **When** they request any agency-scoped resource that belongs to Agency B, **Then** access is denied with a generic not-found or forbidden outcome and no Agency B data is returned.
2. **Given** two agencies with similarly named users, **When** each user signs in, **Then** each sees only their own agency’s membership and settings.
3. **Given** a suspended agency, **When** a member tries to sign in, **Then** sign-in is denied with a clear suspension message and they cannot access that agency’s workspace until the agency is active again; **When** a platform operator uses operator flows for that agency, **Then** they may change lifecycle, invite or provision members, and change roles (auditable), but members still cannot sign in until the agency is **active**; agency administrators cannot sign in to perform those actions while suspended.
4. **Given** an archived agency, **When** a member tries to sign in or operate, **Then** they cannot perform operational work in that agency; **When** an authorized platform operator requests that agency’s audit history, **Then** historical audit records remain available read-only; **When** a platform operator attempts to invite, provision, or change roles for that agency, **Then** the action is denied until the agency is reactivated to **active** or **suspended**; **When** a platform operator reactivates that archived agency to **active** (directly or via **suspended** then **active**) via operator flows, **Then** the lifecycle change is auditable and members with **active** memberships may sign in and operate again once the agency is **active** per normal rules.
5. **Given** a platform operator assigned to an agency, **When** they suspend, reactivate, archive, or reactivate an **archived** agency to **active** (or **suspended** then **active**) via operator flows, **Then** the lifecycle change applies per policy, is auditable, and member access rules in this spec still hold; **Given** an agency administrator, **When** they attempt to suspend, reactivate, archive, or reactivate from **archived**, **Then** the action is denied.

### User Story 3 - Manage agency membership and roles (Priority: P2)

An agency administrator (or platform operator acting on their behalf during early rollout) invites colleagues, assigns roles, and removes access when someone leaves. Role changes take effect without redeploying the application.

**Why this priority**: POC demos require realistic team access patterns; go-live requires self-service governance for the design partner and future customers.

**Independent Test**: Can be tested by creating users with different roles in one agency and verifying each role’s allowed actions match the defined permission set.

**Acceptance Scenarios**:

1. **Given** an agency administrator, **When** they assign a role to a user, **Then** that user’s permitted actions update on next sign-in or within one minute without requiring a full logout of unrelated users.
2. **Given** a user with the read-only member role, **When** they attempt a restricted action (for example changing agency settings, inviting members, or marking a notification as read), **Then** the action is blocked with a clear permission message; **Given** a standard member, **When** they mark an in-app notification as read, **Then** the read state updates and other R1 mutating actions remain denied per role.
3. **Given** a user whose membership in an agency is **removed**, **When** they try to sign in or select that agency, **Then** they no longer have access to that agency’s workspace and must be invited again to rejoin.
3a. **Given** a user whose membership in Agency A is **suspended** (agency otherwise **active**), **When** they attempt to use Agency A as active context or sign in scoped to Agency A, **Then** access is denied with a clear suspension message; **When** they belong to other agencies with valid memberships, **Then** they may still access those other agencies; **When** an agency administrator or platform operator reactivates the membership, **Then** the prior agency role is restored and access resumes (auditable).
3b. **Given** an agency with exactly one agency administrator with **active** membership, **When** that user or another actor attempts to remove, suspend, demote, or reassign roles so that zero **active** agency administrators would remain, **Then** the change is blocked with a clear message and at least one **active** agency administrator remains.
4. **Given** two administrators assign different roles to the same member in quick succession, **When** both changes complete, **Then** the member’s effective role reflects the last successful update (one agency role per membership in R1), each assignment attempt has an audit entry, and duplicate pending invitations for the same person in that agency do not create multiple pending memberships.
5. **Given** an agency administrator or platform operator, **When** they **invite** a user into an agency, **Then** they MUST select exactly one agency role (administrator, standard member, or read-only member) for that invite, membership is **invited** pending explicit acceptance with that role recorded, auditable, and subject to idempotent pending-invite rules; **When** they change the role on a pending **invited** membership before accept, **decline**, revoke, or expiry, **Then** the update is auditable and accept applies the role in effect at accept time; **When** the invitee accepts with matching identity, **Then** membership becomes **active** with that current role; **When** the invitee **declines** with matching identity in the invitation-acceptance experience, **Then** membership becomes **removed**, the decline is auditable, and a new invitation is required to join; **When** they **provision** a user, **Then** they MUST select the agency role, membership is **active** immediately (no accept step), auditable, and targets a specific work-account identity; standard members cannot invite or provision others in R1.
6. **Given** a platform operator, **When** they create, update, or revoke another operator’s agency assignments, **Then** the change succeeds via operator-only flows and is auditable; **When** they grant or revoke **platform operator** status on a work-account identity (separate from agency assignments), **Then** the change succeeds via operator-only flows and is auditable, and revoked identities lose operator capabilities on the next sign-in or session validation; **Given** only one **platform operator** remains, **When** any actor attempts to revoke that identity’s operator status (including self-revoke), **Then** the change is blocked with a clear message and the attempt is auditable; **Given** an agency administrator, **When** they attempt assignment or **platform operator** status changes, **Then** the action is denied.
7. **Given** an agency administrator for an **active** agency, **When** they update the agency display name or primary contact email or phone, **Then** the change is saved, reflected in shell agency context where shown, and auditable; **Given** the same fields on a **suspended** agency, **When** an agency administrator attempts to update them, **Then** the action is denied (administrators cannot sign in to suspended agencies); **Given** a platform operator assigned to a **suspended** or **active** agency, **When** they update those fields via operator flows, **Then** the change is saved and auditable; **Given** a read-only member, **When** they attempt the same, **Then** the action is denied.
8. **Given** a pending invitation that is not accepted within **30 days**, **When** the invitee attempts to use it after expiry, **Then** access is not granted, the invite is treated as expired, and a new invitation is required; expiry or re-invite actions are auditable.
8a. **Given** a pending invitation that has not been accepted, **When** an agency administrator or platform operator revokes it, **Then** the invitation is invalid immediately, the invitee cannot accept unless re-invited, and the revocation is auditable; **Given** a standard or read-only member, **When** they attempt to revoke an invitation, **Then** the action is denied.
8b. **Given** a pending **invited** membership, **When** the invitee **declines** with matching identity, **Then** membership becomes **removed**, the invitation cannot be accepted without a new invite, the decline is auditable, and no inviter in-app notification is generated in R1 (audit only).
9. **Given** a platform operator, **When** they create a new agency in-product with required R1 settings (display name, primary contact email and phone), **Then** the agency is created in **active** status with zero agency memberships allowed until invite or provision, the creating operator is **automatically assigned** to that agency (auditable), the creation is auditable, and they can invite members and use operator flows for that agency; **Given** an agency administrator or standard member, **When** they attempt to create an agency, **Then** the action is denied.
10. **Given** a pending invitation for a specific work-account email, **When** a user signs in with a different identity and attempts to accept or **decline**, **Then** membership is not changed, access is denied with a clear message, and the attempt is auditable; **When** they sign in with the invited identity, **Then** they MUST complete an explicit in-product accept or **decline** action—sign-in alone does not activate **invited** status and does not record **decline**.
10a. **Given** an agency administrator or platform operator, **When** they **invite** or **provision** using a work-account email that is not yet sign-in-capable in the customer’s directory, **Then** the invite or provision is recorded without requiring a directory pre-check; **When** the person later signs in with the matching identity, **Then** **invited** memberships may be accepted per invite rules and **provisioned** **active** memberships grant access per FR-007; **When** they sign in with a non-matching identity, **Then** access is denied without data leakage.
11. **Given** a **standard member** with **active** membership in an **active** agency, **When** they open the agency member list, **Then** they see member names and roles read-only and cannot invite, change roles, or suspend or remove members; **Given** a **read-only member**, **When** they attempt to open the member list or related URLs, **Then** access is denied without data leakage and member-list navigation is not shown; **Given** an **agency administrator** or **platform operator**, **When** they use member management flows, **Then** they may view the roster and perform permitted membership actions per FR-007.

### User Story 4 - Review audit history for accountability (Priority: P2)

Compliance-minded agency leads and platform operators can see who performed sensitive actions (sign-in failures, role changes, agency setting changes, and other security-relevant events defined for this release) and when they occurred.

**Why this priority**: Audit supports security-first operations and partner trust during POC and cutover.

**Independent Test**: Can be tested by performing a defined set of auditable actions and confirming they appear in an agency-scoped audit view with actor, time, and action summary.

**Acceptance Scenarios**:

1. **Given** an agency administrator with **active** membership in an **active** agency, **When** they open the audit view, **Then** they see only events for their agency ordered by most recent first.
2. **Given** a standard member or read-only member in an **active** agency, **When** they attempt to open the audit view or navigate to audit URLs, **Then** access is denied without data leakage and audit navigation is not shown.
3. **Given** a role change, **When** the change completes, **Then** an audit entry records the actor, target user, and new role.
4. **Given** a platform operator assigned to an agency, **When** they open support diagnostics for that agency via operator flows, **Then** they see a read-only agency summary (identity reference, display name, lifecycle status, primary contact fields, membership counts by agency role, most recent agency lifecycle change time) and may open full agency-scoped audit; **When** they attempt diagnostics or audit for an agency they are not assigned to, **Then** access is denied without data leakage; **Then** provisioning actions remain per FR-006/FR-007, member impersonation is not available in R1, the target agency is explicit, infrastructure or service-health telemetry is not shown in R1, and every operator view or provisioning action is auditable.

### User Story 5 - Receive in-app notifications (Priority: P3)

Users see a consistent notification experience in the shared application shell (for example access granted, role changed, or system messages from the platform). They can tell what is unread; standard members mark items as read (items stay in the list in R1—no dismiss or remove).

**Why this priority**: Notifications complete the “operating platform” feel for POC and establish patterns later modules will reuse.

**Independent Test**: Can be tested by triggering a notification event for a user and confirming it appears in the shell, respects agency scope, and updates read state.

**Acceptance Scenarios**:

1. **Given** a new notification for a user in Agency A, **When** they open the app, **Then** they see an unread indicator and can open the notification list scoped to Agency A.
2. **Given** a standard member marks a notification as read, **When** they return later, **Then** it no longer counts as unread and the notification remains in their list; **Given** a standard or read-only member, **When** they attempt to dismiss or remove a notification from the list, **Then** the action is denied in R1; **Given** a read-only member, **When** they attempt to mark a notification as read, **Then** the action is denied with a clear permission message while they may still view notification content where permitted.
3. **Given** a notification belonging to another agency, **When** the user is signed in to Agency A, **Then** that notification never appears in their list.
4. **Given** a defined R1 notification-triggering event for a user (**invited** membership pending acceptance, membership **activated** including via **provision** or invite accept, role changed, membership suspended/reactivated/removed, agency display name or primary contact change affecting displayed context, or agency lifecycle change to **suspended**, **archived**, or **reactivated** to **active** or **suspended** from **suspended** or **archived**), **When** the event is recorded, **Then** the affected user receives an in-app shell notification for their agency (no email or push in R1); **When** agency display name or contact fields change, **Then** agency administrators for that agency may also receive an in-app notice where applicable; **When** agency lifecycle changes, **Then** each user with **active** or **suspended** membership in that agency (including agency administrators) receives an in-app notice, **removed** and **invited-only** users do not, and the lifecycle change remains auditable.
5. **Given** an auditable event that is not in the R1 notification trigger set (for example a failed sign-in by another user or a platform operator cross-agency audit view), **When** the event is recorded, **Then** it appears in audit where authorized but does not generate a user notification unless listed above.

### User Story 6 - Navigate a consistent application shell (Priority: P2)

After sign-in, users see shared navigation, layout, and empty states that future modules (CRM, properties, integrations) will extend. Placeholder areas make it obvious where capabilities will appear without breaking tenancy boundaries.

**Why this priority**: Roadmap POC chains R2/R3/R8 onto this shell; a stable chrome reduces rework.

**Independent Test**: Can be tested by signing in and confirming navigation, header agency context, and module placeholders render consistently for all roles that can access the app.

**Acceptance Scenarios**:

1. **Given** any signed-in user with access, **When** they land on the home area, **Then** they see consistent header, navigation, and agency context across pages.
2. **Given** a signed-in **agency administrator** or **standard member** in an **active** agency, **When** they view the home area, **Then** they see a placeholder summary of coming-soon capabilities (for example CRM and properties) scoped to the active agency and **When** they view main navigation, **Then** no separate nav entries exist yet for those unshipped modules.
3. **Given** a signed-in **read-only member**, **When** they view the home area, **Then** they do not see module-specific coming-soon summaries (generic home/shell only); **Given** a user without permission for a shell area, **When** they view navigation, **Then** entries they cannot access are not shown; direct navigation to forbidden URLs is blocked without data leakage.
4. **Given** a signed-out user, **When** they request an in-app URL, **Then** they are prompted to sign in and are not shown agency data.

### Edge Cases

- When a user’s work account is disabled in their organization’s directory but they still have an active Tenancy Hub membership, the system blocks access on the next sign-in or session/token validation; no operational work is permitted until the directory account is restored or membership is removed.
- Session expiry and failed authentication validation: each signed-in session is independent; concurrent sessions per user are allowed in R1. After **30 minutes** without user activity that resets the idle timer, that session ends and must sign in again; user activity resets the idle timer but that session MUST NOT exceed **12 hours** from its initial sign-in; when either limit is reached or validation fails for a session (including reasonable tolerance for clock skew), that session must re-authenticate, unsaved client state for that session is discarded, and in-flight server operations under that session fail safely without completing under an invalid session. Signing out in one session does not terminate other concurrent sessions.
- When an agency is **suspended**, members cannot sign in to that agency (clear suspension message); the agency remains recoverable. **Only platform operators** may change agency lifecycle (suspend, reactivate, archive, and reactivate from **archived** to **active** or **suspended**) in R1; agency administrators cannot. While suspended, **platform operators** may still invite, provision, and change roles for that agency (auditable); members cannot sign in until the agency is **active**. When an agency is **archived**, members cannot sign in or operate until a platform operator reactivates the agency to **active** (directly or via **suspended** then **active**); **platform operators** MUST NOT invite, provision, or change roles for that agency until it is reactivated to **active** or **suspended** (they may still view audit and change lifecycle); **all** audit events for that agency remain stored and queryable for authorized platform operators (no R1 retention cutoff). Hard delete of agencies or audit data is out of scope for R1.
- Concurrent role updates for the same member in one agency: the last successful update determines the member’s single effective agency role; each attempt is recorded in audit. Duplicate pending invitations for the same identity in the same agency collapse to a single pending membership. Pending invitations expire after **30 days** if not accepted; **agency administrators** and **platform operators** may revoke a pending invitation before acceptance or expiry (immediate invalidation; auditable). Invitees MAY **decline** pending **invited** memberships in the invitation-acceptance experience (matching identity), transitioning to **removed** (auditable; no inviter in-app notification in R1). Expired, revoked, or declined invites cannot be used until a new invitation is issued. Invitation accept or **decline** requires sign-in with the **same work-account email as invited**; mismatched identities are denied and auditable. **Invite** and **provision** MAY target a work-account email even if that identity is not yet sign-in-capable in the customer’s directory; no directory existence check at create time—access follows matching sign-in (and invite accept for **invited**).
- When a user switches active agency, the new agency context applies immediately: unsaved or in-flight UI work for the prior agency is discarded, and server operations must not complete under the wrong agency (stale requests are rejected or fail safely).
- When a multi-agency user’s last-used agency is no longer valid (for example membership **removed** or **suspended**, agency suspended or archived, or operator assignment revoked), sign-in MUST NOT default to that agency; the user MUST choose a remaining valid agency (or see no-access messaging if none remain). **Invited** memberships alone do not qualify as valid shell context; users with only **invited** memberships (and no **active** membership or operator path) MUST complete explicit per-invite acceptance after sign-in before entering the routine agency shell. A **platform operator** with zero agency assignments and no agency memberships MAY sign in and use operator-only global flows (create agency, manage operator assignments) with no active agency context until assigned (including auto-assign on agency create); agency-scoped shell and target-agency operator flows remain blocked without an assignment.
- **Suspended** agency membership (distinct from agency-level suspension): blocks access to that agency only while preserving membership and role for reactivation; **removed** ends access and requires a new invitation. Suspend, reactivate, and remove membership actions MUST be auditable. Agency administrators and platform operators MAY suspend, reactivate, or remove memberships per FR-007.
- A newly created **active** agency MAY have zero agency memberships (and thus zero agency administrators) until the first member is invited or provisioned. Once an agency has at least one **active** agency administrator membership, an **active** agency MUST always retain at least one **active** agency administrator; role or membership changes that would reduce the count of **active** agency administrators to zero MUST be rejected (auditable where applicable), including suspend or remove of the last active administrator.
- **Platform operator** status: at least one **platform operator** MUST always remain in the product in R1; revoke or self-revoke that would leave zero operators MUST be blocked (auditable attempt). Initial operators may be seeded outside the product before this guard applies.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST authenticate users through organizational work accounts aligned with Microsoft 365 sign-in used by UK letting agencies, and MUST treat a disabled directory account as loss of access on the next sign-in or session/token validation even if Tenancy Hub membership remains active. The same user MAY hold **multiple concurrent signed-in sessions** (for example separate browsers or devices); each session is independent and MUST enforce idle and absolute lifetime limits on its own. Sessions MUST end after **30 minutes** without user activity that resets the idle timer; user activity MUST reset that idle timer but MUST NOT extend the session beyond **12 hours** after initial sign-in for that session; when either idle or absolute limit is reached or session/token validation fails for a session, that session MUST require sign-in again, unsaved client state for that session MUST be discarded, and in-flight operations under that session MUST fail safely without completing under an invalid session. Sign-out in one session MUST NOT automatically sign the user out of other concurrent sessions in R1.
- **FR-002**: System MUST bind every authenticated session to exactly one active agency context at a time when the user is performing routine agency-scoped shell work. Routine agency-scoped shell work MUST require **active** agency membership (or valid platform-operator assignment context per FR-006); **invited** membership alone MUST NOT grant agency shell access until the user completes explicit in-product acceptance per FR-007. A signed-in **platform operator** with **no** agency assignments and **no** valid agency membership MAY have **no** active agency context and MUST still access permitted operator-only global flows in R1 (create agency per FR-016, manage platform operator agency assignments and **platform operator** status per FR-006)—without agency data leakage. Users with multiple agency memberships MUST enter the shell with last-used agency as active context when that agency remains valid (agency **active** and user membership **active**, not **suspended**, **removed**, or **invited** only); they MUST be able to switch agency in the shell without signing out. Switching MUST re-scope the session immediately, discard unsaved client state for the prior agency, and reject or fail safely any operation not valid for the newly active agency. The same work-account identity MAY simultaneously be a **platform operator** and hold one or more agency memberships in R1; operator privileges and agency role permissions MUST be enforced separately (operator-only flows and assignments vs shell active agency context and membership role). Platform operators with one or more assignments MUST use the same last-used-default and switch model for shell work among agencies explicitly assigned to that operator, MUST not activate or target unassigned agencies, and MUST access assigned agencies through operator-only flows that name the target agency and are auditable (no member impersonation).
- **FR-003**: System MUST enforce agency isolation for all agency-scoped data and operations; no user action in Agency A may expose or modify Agency B data.
- **FR-004**: System MUST support lifecycle states for an agency (at minimum: active, suspended, archived) that gate member access. **Only platform operators** MAY transition an agency between lifecycle states in R1 (including suspend, reactivate from **suspended** to **active**, archive, and reactivate from **archived** to **active** or to **suspended** then **active**); agency administrators and other member roles MUST NOT. **Suspended** agencies MUST deny member sign-in with a clear message while remaining recoverable by platform operators; **platform operators** MAY still invite, provision, and change roles for that agency via operator flows (auditable), but members MUST NOT sign in or operate in the workspace until the agency is **active** again. **Archived** agencies MUST deny member sign-in and operational access until reactivated by a platform operator per above, MUST NOT allow invite, provision, or role changes for that agency until reactivated to **active** or **suspended**, while retaining durable audit history readable per policy throughout **archived** and after reactivation. Every agency lifecycle transition MUST be auditable.
- **FR-005**: System MUST assign each agency membership **exactly one** agency role (administrator, standard member, or read-only member) at **invite** or **provision** time, retained for **invited**, **active**, and **suspended** statuses, that determines permitted actions within that agency in R1; role changes replace the prior role rather than stacking multiple agency roles. Platform operator capabilities MUST remain governed by operator identity and agency assignments, not by combining agency roles on the same membership.
- **FR-006**: System MUST provide a minimum role set for POC: agency administrator (manage membership and roles within the agency; view agency-scoped audit for **active** agencies), standard member (operational access to assigned shell areas; in R1 may view the agency member list read-only—names and roles only—and may mark in-app notifications read; **no** audit access and **no** membership changes), read-only member (view permitted shell areas and notifications without mutating agency settings, membership, roles, notification read state, **member-list** access, or **audit**), and platform operator (provisioning and read-only support views such as audit and diagnostics **only for agencies explicitly assigned to that operator**—**no** impersonation of agency member sessions in R1). A single work-account identity MAY hold platform operator status and one or more agency memberships at once; effective permissions MUST derive from the relevant context (operator assignment flows vs active agency membership role), not by stacking operator onto the same membership record. **Only platform operators** MAY create, update, or revoke platform operator agency assignments, and MAY grant or revoke **platform operator** status on work-account identities (separate from agency assignments), via auditable operator-only flows; agency administrators MUST NOT manage operator assignments or **platform operator** status in R1. Revoking **platform operator** status MUST remove operator capabilities on the next sign-in or session/token validation (agency memberships and assignments remain governed separately). The system MUST NOT allow revoke or self-revoke of **platform operator** status when it would leave **zero** platform operators in the product; such attempts MUST be blocked with a clear message and MUST be auditable.
- **FR-007**: System MUST allow **agency administrators** and **platform operators** (and no other roles in R1) to invite or provision users into an agency; to **revoke** pending invitations before acceptance or expiry; to **suspend**, **reactivate**, or **remove** agency membership; and to change a member’s single agency role—except while the agency is **archived**, when invite, provision, and role changes MUST be denied for all actors until the agency is reactivated to **active** or **suspended** (per FR-004). **Invite** MUST create membership in **invited** status pending acceptance and MUST record exactly one agency role (administrator, standard member, or read-only member) chosen by the inviter at invite time; explicit accept with matching identity MUST transition the membership to **active** with that role (auditable). The invitee MUST be able to **decline** a pending **invited** membership via an explicit in-product action in the invitation-acceptance experience with matching identity; **decline** MUST transition membership to **removed**, MUST be auditable, MUST NOT grant agency access, and MUST require a new invitation to join; **decline** MUST NOT generate an inviter in-app notification in R1 (audit only). **Provision** MUST create membership in **active** status immediately (no accept step) with exactly one agency role chosen at provision time. Both paths MUST target a specific work-account email identity, MUST be auditable, and MUST obey idempotent pending-invite rules for **invited** status only. The system MUST NOT require the target identity to exist or be enabled in the customer’s directory at invite or provision time; agency access for that membership MUST be granted only when sign-in succeeds with the matching work-account identity (and **invited** accept rules where applicable). **Suspended** membership MUST block access to that agency (clear message) while retaining membership and role for reactivation without a new invitation; **removed** membership MUST end access and require a new invitation or provision to rejoin. Revoke, suspend, reactivate, remove, and role changes MUST be auditable. Duplicate pending invitations for the same identity in the same agency MUST be idempotent (at most one pending **invited** membership). **Agency administrators** and **platform operators** MAY change the agency role on an **invited** membership until accept, **decline**, revoke, or **30-day** expiry; each change MUST be auditable, and accept MUST apply the role in effect at accept time. Each **invited** membership MUST match acceptance sign-in to the invited work-account email—otherwise access MUST be denied and the failed attempt MUST be auditable. Activating an **invited** membership MUST require an explicit in-product accept action after successful sign-in with matching identity; sign-in alone MUST NOT transition **invited** to **active**. **Invited** memberships MUST expire **30 days** after creation if not accepted; expired or revoked invites MUST NOT grant access until a new invitation is issued. **Provisioned** **active** memberships are not subject to invite acceptance or **30-day** invite expiry (removal or suspension still apply per policy). Concurrent role updates for the same member MUST apply last successful update with an audit entry per attempt. Once an agency has at least one **active** agency administrator membership, the system MUST NOT allow any membership or role change that would leave an **active** agency with zero **active** agency administrators; such attempts MUST be blocked with a clear message (including self-suspension, self-removal, or self-demotion of the last active administrator). New **active** agencies with zero memberships are exempt until the first agency administrator is provisioned or invited and activated.
- **FR-008**: System MUST record audit events for security-relevant actions including successful and failed sign-in attempts, agency creation, agency membership changes, role changes, agency status changes, agency setting changes (display name and primary contact email or phone), platform operator agency assignment changes, and **platform operator** status granted or revoked on a work-account identity. Audit events MUST be retained for the agency’s entire lifetime (active, suspended, archived) with **no time-based purge or hiding** in R1.
- **FR-009**: System MUST present agency-scoped audit history in R1 **only** to agency administrators with **active** membership while the agency is **active**, and read-only audit plus **support diagnostics** for platform operators **only on agencies assigned to that operator** (including **suspended** and **archived** assigned agencies’ full retained audit history via operator flows). In R1, **support diagnostics** MUST be limited to a read-only **agency summary**: internal agency identity reference, display name, lifecycle status, primary contact email and phone, membership counts broken down by agency role (administrator, standard member, read-only member, and **invited** pending), and timestamp of the most recent agency lifecycle change, with navigation or access to full agency-scoped audit for that agency. Infrastructure health, dependency status, and distributed tracing or service telemetry MUST NOT be part of R1 diagnostics. **Standard members** and **read-only members** MUST NOT access audit views, diagnostics, or data in R1. Every platform-operator access outside the operator’s active shell context MUST be auditable, and member impersonation MUST NOT be offered in R1.
- **FR-010**: System MUST deliver notifications to users only through the signed-in application shell within their active agency context, with read/unread state per user. Notifications MUST remain in the user’s list in R1 (no dismiss or remove). **Standard members** MAY mark their notifications read; **read-only members** MUST NOT change notification read state (view only). Email, SMS, and push delivery are out of scope for R1. In R1, the system MUST generate in-app notifications for the **affected user** when: an **invite** leaves membership **invited** pending their acceptance; membership becomes **active** (including via **provision** or invite acceptance); their agency role changes; their membership is **suspended**, **reactivated**, or **removed**; agency **display name** or **primary contact email or phone** changes in a way that affects displayed agency context; or the agency’s lifecycle changes to **suspended**, **archived**, or is **reactivated** to **active** or **suspended** from **suspended** or **archived**. For agency lifecycle notifications, each user with **active** or **suspended** membership in that agency (including agency administrators) MUST receive an in-app notice; users with **removed** membership or **invited-only** status MUST NOT. Agency **administrators** MAY also receive in-app notices for agency display name or contact changes where applicable. Other auditable events MUST NOT automatically generate user notifications unless added in a later release.
- **FR-011**: System MUST provide a shared signed-in application shell (layout, navigation, agency context, sign-out) that later feature modules can extend without redefining tenancy rules. Navigation MUST omit items the signed-in user is not permitted to access in R1 (no disabled tease for forbidden areas). Unshipped roadmap modules MUST NOT appear as navigation entries in R1. In R1, only **agency administrators** and **standard members** with **active** membership in an **active** agency MAY see a single home/dashboard coming-soon summary of those modules for the active agency; **read-only members** MUST NOT see module-specific coming-soon summaries on the home area. All user-facing shell, invitation-acceptance, operator-flow, and error or permission messages in R1 MUST be **English only** with no in-product language selector; dates and numbers MUST use UK English conventions. Additional languages and localization are out of scope for R1.
- **FR-012**: System MUST expose stable tenancy boundaries (agency identity, membership, roles, and isolation guarantees) that downstream domain features depend on without duplicating tenancy logic.
- **FR-013**: System MUST fail safely on authorization errors—no partial data leakage in error messages or client responses.
- **FR-014**: System MUST persist agency, membership, role, audit, and notification data durably so restarts do not erase tenancy state.
- **FR-015**: System MUST support R1 agency settings limited to **display name** and **primary contact email and phone**. Agency **display names** MUST NOT be required to be globally unique in R1; multiple agencies MAY share the same display name, and the internal agency identity is canonical for isolation and operator targeting. Platform operators MAY set these when provisioning an agency and MAY update them thereafter on **assigned** agencies via operator flows (including while the agency is **suspended** or **active**; not while **archived** unless a future policy explicitly allows). Agency administrators MAY update them only while the agency is **active** and their membership is **active**. Read-only members and standard members MUST NOT change them in R1. Additional agency configuration (time zone, branding, billing) is out of scope for R1.
- **FR-016**: System MUST allow **platform operators only** to create new agencies in-product in R1 (initial status **active**, with display name and primary contact email and phone). A new **active** agency MAY have zero agency memberships until members are invited or provisioned; the at-least-one-**active**-agency-administrator rule in FR-007 applies only after at least one **active** agency administrator membership exists. Agency creation MUST be auditable. Self-service agency signup by non-operators MUST NOT be offered in R1. When an operator creates an agency, the system MUST **automatically assign that operator** to the new agency (auditable) so they can manage and provision it immediately without a separate assignment step.

### Key Entities *(include if feature involves data)*

- **Agency**: A letting agency tenant; has a canonical internal agency identity, display name (not required to be globally unique in R1), primary contact email and phone, and lifecycle status (active, suspended, archived). Lifecycle transitions in R1 are performed by platform operators only (including reactivation from **archived** to **active** or **suspended**). Suspended and **archived** agencies block member sign-in until the agency is **active** again; while **suspended**, platform operators may still manage membership; while **archived**, invite, provision, and role changes are blocked until reactivation to **active** or **suspended**. Audit history is retained for the agency’s lifetime. R1 in-product settings are limited to display name and primary contact fields above.
- **Agency membership**: Links a person’s identity to an agency with status (**invited**, **active**, **suspended**, or **removed**) and **exactly one** agency role (administrator, standard member, or read-only member) assigned at **invite** or **provision** time and retained while **invited**, **active**, or **suspended** (role on **invited** may be updated by agency administrators or platform operators until accept, **decline**, revoke, or expiry). **Invited** is created by **invite** (pending explicit in-product accept or **decline** after sign-in; revocable before accept, **decline**, or **30-day** expiry; accept requires matching work-account email plus explicit user accept—not automatic activation on sign-in alone; accept activates with the role in effect at accept time; **decline** with matching identity transitions to **removed** and requires a new **invite**). **Active** may be created immediately by **provision** (no accept step) or by accepting an **invite**. **Suspended** blocks agency access until reactivated; **removed** ends access until a new **invite** or **provision**.
- **Role**: Named permission bundle within an agency (administrator, standard member, or read-only member for agency memberships; platform operator is a separate trusted identity with per-agency assignments, not an additional agency role stacked on the same membership in R1); maps to allowed action categories for POC shell areas. In R1, **standard members** may view the agency member roster read-only; **read-only members** may not.
- **Audit event**: Immutable record of who did what, for which agency, at what time, with a human-readable summary. Retained for the agency’s lifetime in R1 (no rolling retention window or purge).
- **Notification**: Agency-scoped in-app message to a user with content, created time, and read state (R1 channel: shell only). R1 triggers include **invited** membership pending acceptance, membership **activation** (including **provision** or invite accept), role change, membership suspend/reactivate/remove, agency display or contact changes affecting displayed context (admins may be notified on the latter), and agency lifecycle change to **suspended**, **archived**, or **reactivated** to **active** or **suspended** from **suspended** or **archived** (for users with **active** or **suspended** membership in that agency). Items persist in the user’s list in R1 (no dismiss or remove). Read-state updates are allowed for standard members only; read-only members may view but not mark read.
- **User identity**: The work-account identity used for sign-in; distinct from membership per agency. The same identity MAY be flagged as a **platform operator** while also holding agency memberships; operator and member capabilities remain separate. **Platform operator** status is granted or revoked in R1 only by other **platform operators** through auditable operator-only flows (initial operators may be seeded outside the product).
- **Platform operator assignment**: Links a platform operator identity to one or more agencies they may activate in the shell or target in operator provisioning and support flows; unassigned agencies are inaccessible to that operator. Created and maintained in R1 only by platform operators through auditable operator-only management (initial POC assignments may be seeded outside the product). Creating an agency automatically creates an assignment for the creating operator.
- **Operator agency summary (R1 diagnostics)**: Read-only operator view for an assigned agency comprising identity reference, display name, lifecycle status, primary contact fields, per-role membership counts (including **invited** pending), most recent agency lifecycle change time, and access to that agency’s audit history; excludes infrastructure or service telemetry in R1.

A platform operator with **no** assignments may sign in without active agency context and use global operator flows (create agency, manage operator assignments) until assigned. The same work-account MAY be both a **platform operator** and an agency member; operator tooling and agency membership permissions MUST NOT be conflated. Platform operators are a small trusted group; **platform operator** status and **explicit per-operator agency assignments** are managed in-product only by other platform operators (auditable; initial operators may be seeded outside the product); agency administrators cannot grant operator status or change operator assignments. Shell context and target-agency operator flows are limited to assigned agencies, with read-only **agency summary** diagnostics (per FR-009) and audit via explicit target-agency flows—no infrastructure or service-health telemetry in R1; member session impersonation is out of scope for R1 and every operator access to an assigned agency is auditable.
- Data residency and formal compliance certifications (for example ISO) are product-level concerns documented elsewhere; R1 must still meet isolation and audit behaviors above.
- User-facing copy in R1 (shell, operator flows, invitation acceptance, permission and lifecycle messages) is **English only** with UK English date and number conventions; no language selector; translation and multi-locale support are deferred.
- Session idle timeout is **30 minutes** without activity that resets the idle timer; activity resets idle timing but absolute session length is capped at **12 hours** from initial sign-in **per session**; users MAY have multiple concurrent sessions (each subject to its own idle and 12-hour limits); sign-out in one session does not end other sessions in R1. After either limit or any failed session/token validation for a given session, that session requires re-authentication and loses unsaved client state while in-flight operations under that session fail safely. Step-up re-authentication for sensitive changes may be refined in security review but is not separately specified here.
